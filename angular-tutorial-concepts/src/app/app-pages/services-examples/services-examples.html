Interview questions

Q1. Why do we use services in Angular?

Services help separate concerns, reuse logic, share data and centralize functionality such as API calls and business rules.

Q2. Can we use a service without @Injectable()?

A class without @Injectable() can sometimes be injected if it has no dependencies and is provided appropriately. However, @Injectable() is the standard and recommended approach for services, particularly when they have dependencies or use Angular's DI features.

Q3. Should all business logic be written in services?

Not necessarily. Component-specific UI behavior belongs in components. Reusable business logic and data operations are good candidates for services. The goal is clear responsibility, not moving every method out of a component.

providedIn: 'root' and Service Providers

A provider tells Angular how to resolve a dependency. For services, the provider configuration determines where the service is registered and which instances are available.

This tells Angular to provide the service at the root application injector.

Interview questions

Q1. What is the difference between providedIn: 'root' and component-level providers?

providedIn: 'root' registers a service application-wide through the root injector. Component-level providers register a service in a particular component's injector, allowing a separate instance for that component subtree.

Q2. What is providedIn: 'platform'?

It registers a service in the platform injector, which can be shared by applications running on the same Angular platform instance. It is a specialized option rather than the usual choice for ordinary application services.

Q3. What is tree-shakable dependency injection?

When services are provided using mechanisms such as providedIn: 'root', Angular's build tools can eliminate unused services from the production bundle when they are not referenced by the application.

4. Hierarchical Dependency Injection

Angular DI is hierarchical. Instead of having only one injector, Angular has injector hierarchies that determine which provider supplies a dependency.

For modern standalone Angular applications, the main concepts are:

  • Environment injectors: Used for application-level and route-level provider scopes.
  • Element injectors: Associated with components and directives in the component tree.

A component can resolve dependencies from its own injector or from an ancestor injector.

Interview questions

Q1. What is hierarchical dependency injection?

It is Angular's mechanism for organizing providers across injector hierarchies. It allows different parts of an application to share services or use scoped instances.

Q2. What happens if the same service is provided in root and in a child component?

The child component and descendants resolving from its provider get the child-scoped instance. Other parts of the application resolving from the root continue to use the root instance.

Q3. Why is hierarchical DI useful?

It supports scoped state and behavior. For example, separate instances of a form-state service can be created for different editor components without sharing their internal state.

Interview questions

Q1. Why do we need InjectionToken?

It provides a runtime token for dependencies that are not classes, such as interfaces, configuration values and primitive types.

Q2. What is the difference between useClass and useExisting?

useClass tells Angular to instantiate a class for a token. useExisting aliases an existing provider token, so both tokens resolve to the same instance when they refer to that provider.

Q3. When would you use useFactory?

Use it when the provided value depends on runtime conditions, configuration, or other injected dependencies and needs to be created by a function.

6. inject() vs Constructor Injection

Angular supports two common ways to obtain dependencies.

Constructor injection

constructor(private employeeService: EmployeeService)

The dependency is declared as a constructor parameter.

The inject() function

private employeeService = inject(EmployeeService);

inject() retrieves a dependency from the active injection context. It is commonly used in field initializers, provider factories, guards and other supported injection contexts.

Interview questions

Q1. Which is better: constructor injection or inject()?

Both are valid. Constructor injection is familiar and explicit, while inject() can make field-based dependencies and functional APIs more convenient. Follow the conventions of the codebase and choose the approach that keeps dependencies clear.

Q2. Can inject() be called inside any method?

No. It must be called in an Angular injection context, such as a constructor, field initializer, provider factory or supported functional API. Calling it later in an arbitrary method usually produces an injection-context error.

Q3. Can we use inject() in a functional route guard?

Yes. Functional route guards execute in an injection context, so they can use inject() to obtain services.

                
                    export const authGuard: CanActivateFn = () => 
                        const authService = inject(AuthService);
                        const router = inject(Router);

                        return authService.isLoggedIn
                            ? true
                            : router.createUrlTree(['/login']);
                        ;

A shared service is useful when components are unrelated in the component tree or when multiple components need access to the same application state.

Interview questions

Q1. How do you share data between unrelated components?

Use a shared service with Signals, Observables or another state management mechanism. This avoids tightly coupling unrelated components.

Q2. What is the difference between using a shared service and using @Input() and @Output()?

Inputs and outputs are suited to direct parent-child communication. A shared service is useful for unrelated components or state that needs to be accessed from multiple places.

Q3. Should a shared service expose writable signals publicly?

For state that should be centrally managed, it is often better to keep writable signals private and expose read-only signals. This prevents consumers from changing state without going through the service's intended methods.

8. Singleton Services and Service Instances

A singleton service means a service has one shared instance within a particular injector scope.
A service with providedIn: 'root' normally behaves as a singleton within that application's root injector.
However, singleton does not mean there can only ever be one instance of that service class in the entire application. Providing the same service at component or route level can create additional instances.

Both components use the root-provided service instance, so the count is shared.
If you add providers: [CounterService] to CounterAComponent, it gets its own instance instead.

Interview questions

Q1. Is every Angular service a singleton?

No. The instance lifecycle depends on where and how the service is provided.

Q2. How can you accidentally create multiple instances of a service?

By providing the service in multiple component injectors or other injector scopes. A common mistake is adding a root-provided service again to a component's providers array without intending to create a separate instance.

Q3. What is a practical use case for multiple service instances?

A reusable editor component may need its own editing state. Providing an editor-state service at the editor component level lets each editor maintain independent state.
