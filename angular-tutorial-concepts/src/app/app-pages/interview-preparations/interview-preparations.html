Q4. Pure vs Impure Pipes

A pure pipe is the default. It executes when Angular detects a change to its input value or reference. An impure pipe can execute during every relevant change-detection cycle.

            
                Pure pipe	                    Impure pipe
                Default	                        Requires pure: false
                Runs on input changes	        Can run frequently
                Usually more efficient	        May be more expensive
                Good for most transformations	Appropriate only for specific cases

A Pure Pipe is a pipe that Angular executes only when the input value or input reference changes. Pure pipes are optimized for performance because Angular avoids running them unnecessarily. By default, all Angular pipes are Pure Pipes.

                @Pipe(
                name: 'myPipe',
                pure: true
                )

An Impure Pipe is a pipe that Angular executes during every change detection cycle, regardless of whether the input reference changed or not. Impure pipes are useful when data changes internally without creating a new object or array reference.
The important part:
pure: false
This tells Angular to run the pipe on every change detection cycle.

                @Pipe(
                name: 'myPipe',
                pure: false
                )

Q5. Can we chain pipes?

Yes. The output of one pipe can be passed to another.

Yes. Parameters are passed after the pipe name using colons.

Q7. Why should expensive operations be avoided inside pipes?

Pipes can be evaluated as part of template update processing. Expensive transformations, especially in impure pipes, can affect rendering performance. Complex calculations may be better placed in a service or derived state.

Q. You need to filter and sort a large table. Would you use a custom pipe?

For a small, simple list, a pure custom pipe may be appropriate. For large data, frequent updates, or server-backed filtering, I would consider derived state, a dedicated data-processing layer, or server-side operations to avoid repeated expensive calculations.

2. What is an Observable?

An Observable represents a stream of values that can arrive over time.
For example, an API might return data once, while a search input may emit values repeatedly.

Observable lifecycle

  1. Observable: Produces values over time
  2. Observer: Receives values, errors, and completion
  3. next() Emits a value
  4. error() Signals failure
  5. complete() Signals the end

An Observable can emit zero or more values, followed by either completion or an error. Once it completes or errors, it cannot emit further notifications.

An Observer is the object that receives notifications from an Observable.

Observable vs Observer

4. What is subscribe()?

A normal Observable does not necessarily allow you to push values into it manually. A Subject is both an Observable and an Observer: you can subscribe to it and call next() to emit values.

A ReplaySubject can replay a configured number of previous values to new subscribers.

AsyncSubject

An AsyncSubject emits only the last value, and only when it completes.

9. Higher-order mapping operators

This is one of the highest-priority RxJS interview topics.

A higher-order Observable is an Observable that emits other Observables. Mapping operators determine how those inner Observables are handled.

The four operators to understand are:

  • switchMap
  • mergeMap
  • concatMap
  • exhaustMap

switchMap()

Switches to the latest inner Observable and unsubscribes from the previous inner subscription.

Use case: Search boxes, where older searches become irrelevant when a newer term arrives.

mergeMap()

Subscribes to multiple inner Observables concurrently.

Use case: Independent API requests that can run concurrently.

concatMap()

Processes inner Observables sequentially, waiting for each to complete before starting the next.

Use case: Operations that must be processed in order, such as sequential updates.

exhaustMap()

Ignores new source emissions while the current inner Observable is still active.

Use case: Preventing repeated login submissions while one login request is in progress.

The most important comparison

                
Operator	Handles a new emission by…	                    Typical use
switchMap	Replacing the previous inner subscription	    Search suggestions
mergeMap	Running concurrently	                        Independent requests
concatMap	Queueing in order	                            Sequential operations
exhaustMap	Ignoring it while busy	                        Preventing duplicate submissions

Important nuance: Unsubscribing from an Angular HTTP Observable usually aborts the client-side request. It does not guarantee that the backend has stopped processing an operation that it has already received. For important writes, backend-side idempotency and validation still matter.

10. Combining multiple Observables

forkJoin()

Waits for all supplied Observables to complete, then emits their final values together.

Use case: Loading several independent API resources before preparing a dashboard.

Note that if one source errors, forkJoin errors unless you handle that source's error. If a source never completes, forkJoin does not emit.

combineLatest()

Emits a combined latest-value result whenever any input emits, after every input has emitted at least once.

Use case: Reacting to multiple filters or form controls.

If a source is a BehaviorSubject, its current value is emitted immediately to a new subscriber. For form controls, you may use startWith() when you need the current value included.

zip()

Pairs values by their emission index: the first value from each source, then the second from each, and so on.

11. debounceTime() and distinctUntilChanged()

These operators are very common in search and reactive forms.

debounceTime()

Waits until a specified period passes without a new emission, then emits the latest value.

This reduces requests while the user is typing.

distinctUntilChanged()

Suppresses consecutive duplicate values.

By default, it uses === comparison, so objects generally require a custom comparator if you want structural comparison.

Interview question: Why use both operators together?

12. Error handling: catchError(), retry(), finalize()

catchError()

Catches an Observable error and returns another Observable, such as a fallback or a rethrown error.

Here, a failed request becomes an empty array. This is appropriate only if an empty list is a safe fallback for the application; otherwise, preserve the error for the UI to handle.

retry()

Resubscribes to the source after an error, for a configured number of attempts.

retry(2) allows up to two retries after the original attempt. Use it selectively for transient errors; don't blindly retry validation failures or non-idempotent write operations.

finalize()

Runs cleanup when the stream completes, errors, or is unsubscribed.

Remember: catchError() handles errors, retry() retries, and finalize() performs cleanup.

13. Subscription management and memory leaks

A memory leak can occur when a long-lived Observable subscription remains active after the component is destroyed and continues retaining or updating resources.

Option 1: takeUntilDestroyed() — recommended for modern Angular

The subscription is cleaned up when the component or injection context is destroyed.

Option 2: takeUntil()

This traditional pattern uses a notifier Observable to terminate a subscription.

Option 3: take()

Automatically completes after receiving a specified number of values.

Interview question: Should we manually unsubscribe from every HTTP request?

Usually not for standard finite Angular HTTP Observables because they complete after their response or error. However, subscriptions to long-lived streams, such as valueChanges, interval, or a Subject, should be managed when their lifetime exceeds the component's lifetime.

Section 8: Change Detection and OnPush

1. What is change detection?

Definition: Change detection is the process Angular uses to determine whether the data displayed in a component's template needs to be updated.

When the user clicks the button:

  1. increment() executes.
  2. The value of count changes.
  3. Angular checks the relevant view.
  4. The displayed count updates.

Without a suitable change-detection notification, changing a property alone does not necessarily cause Angular to refresh the view immediately.

2. Default change detection

Angular's default strategy checks views as part of its normal change-detection process. In traditional Zone.js-based applications, asynchronous activity such as events, timers, and HTTP responses can trigger a change-detection cycle.

With the default strategy, Angular checks the component's view during its normal change-detection process.

Interview point: Change detection does not mean Angular automatically re-renders the entire DOM every time. Angular evaluates bindings and updates the DOM where values have changed.

3. What is OnPush?

OnPush is a change-detection strategy that allows Angular to skip checking a component subtree in situations where Angular has no reason to check it.

With OnPush, Angular can check the component when, for example:

  • A template-bound input changes according to Angular's input-change semantics.
  • An event occurs in the component's view.
  • A signal read by the template changes.
  • An Observable consumed through AsyncPipe emits.
  • The view is explicitly marked for checking.

Convenient for general-purpose components.	    |Useful for optimizing suitable components.

Important: OnPush does not mean a component is checked only once. Angular can check it again whenever a relevant trigger marks it for checking.

8. AsyncPipe and change detection

The AsyncPipe subscribes to an Observable or Promise and exposes its latest value to the template. When a new value arrives, it marks the view for checking.

This is particularly useful with OnPush, because you don't need to manually subscribe and call markForCheck() just to display the stream's latest value.

  • AsyncPipe emissions.
  • Marking a view for checking.
  • Other supported Angular change-detection notifications.

No. Signals and zoneless change detection are separate concepts. Signals can be used in applications with or without Zone.js.

2. What is NgRx?

NgRx is a state-management library for Angular inspired by Redux and built around RxJS. It helps manage shared application state through predictable, centralized updates.

The core NgRx Store pattern uses five important concepts:

  1. Component: Dispatches an action

  5. Selector: Selects the data needed by the component
  6. Component updates its UI
  7. Effects handle side effects such as HTTP requests and dispatch success or failure actions.

1. Actions

Plain descriptions of events or intentions, such as increment, loadEmployees, or loadEmployeesSuccess.
They don't directly modify state.

2. Reducers

Pure functions that receive the current state and an action, then return the next state without mutating the original.

3. Store

The central container that holds application state and exposes APIs to dispatch actions and select state.

4. Selectors

Reusable functions for reading specific parts of the state. Memoized selectors can avoid unnecessary recalculation when their inputs haven't changed.

5. Effects

Handle side effects such as API calls, then dispatch new actions containing the results or errors.

9. Important NgRx interview questions and answers

                
Q1. What is the difference between an action and a reducer?
Answer: An action describes an event that occurred. A reducer defines how the current state changes in response to that action.

Q2. Why must reducers be pure functions?
Answer: Pure reducers produce predictable state updates, are straightforward to test, and avoid hidden side effects. They should not mutate existing state or perform HTTP requests.

Q3. What is the difference between a selector and an effect?
Answer: A selector reads or derives state. An Effect handles side effects such as API requests and can dispatch a resulting action.

Q4. Can we call an API inside a reducer?
Answer: No. Reducers must remain pure and synchronous. API requests belong in services, orchestrated by Effects when using NgRx.

Q5. What is the difference between createAction() and createReducer()?
Answer: createAction() defines an event, while createReducer() defines the state transitions associated with actions.

Q6. Why use props()?
Answer: props() defines the payload an action can carry, such as an employee ID, form data, or an API response.

Q7. What happens when an API request fails in an Effect?
Answer: The Effect should handle the error and emit a failure action. The reducer can then update the error and loading state. Handling the error inside the request's inner Observable also allows the outer Effect stream to continue listening for future actions.

Q8. What is memoization in NgRx selectors?
Answer: A memoized selector can reuse a previous derived result when its input values or references have not changed. This avoids unnecessary calculations.

Q9. What is the difference between switchMap() and exhaustMap() in an Effect?
Answer: switchMap() switches to the latest inner Observable and unsubscribes from the previous one. exhaustMap() ignores new source emissions while the current inner Observable is active.

Q10. Is NgRx required in every Angular project?
Answer: No. For simple applications, component state, services, or Signals may be sufficient. NgRx is useful when shared state, complex workflows, debugging, and predictable state transitions justify the additional structure.
