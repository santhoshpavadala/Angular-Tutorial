NgRx & State Management

1. What is state management in Angular?

State is the data that an application needs to remember and display as users interact with it.

Examples in an enterprise Angular application:

  • Logged-in user details and permissions.
  • Employee lists retrieved from REST APIs.
  • Dashboard filters and selected assets.
  • Loading, success, and error states.
  • Shopping cart items or application settings.

State management is the process of storing, updating, sharing, and tracking that data predictably across an application.

Different ways to manage state

                
Approach	            Best suited for
Component properties	Data used by one component
@Input() / @Output()	Parent-child communication
Angular service	        Shared data and business logic
Signals in a service	Reactive shared state with relatively little boilerplate
NgRx Store	            Complex, shared state with predictable updates
NgRx Effects	        Asynchronous operations such as API requests

Interview tip: Don't say every Angular application needs NgRx. Choose the simplest approach that meets the application's complexity, testing, and maintenance needs.

2. What is NgRx?

NgRx is a state-management library for Angular inspired by Redux and built around RxJS. It helps manage shared application state through predictable, centralized updates.

The core NgRx Store pattern uses five important concepts:

  1. Component: Dispatches an action
  2. Action: Describes what happened
  3. Reducer: Calculates the next state immutably
  4. Store: Holds the updated application state
  5. Selector: Selects the data needed by the component
  6. Component updates its UI
  7. Effects handle side effects such as HTTP requests and dispatch success or failure actions.
    Effects work alongside the action/reducer flow; they are not a step every action must pass through.

3. The five main NgRx concepts

1. Actions

Plain descriptions of events or intentions, such as increment, loadEmployees, or loadEmployeesSuccess.
They don't directly modify state.

2. Reducers

Pure functions that receive the current state and an action, then return the next state without mutating the original.

3. Store

The central container that holds application state and exposes APIs to dispatch actions and select state.

4. Selectors

Reusable functions for reading specific parts of the state. Memoized selectors can avoid unnecessary recalculation when their inputs haven't changed.

5. Effects

Handle side effects such as API calls, then dispatch new actions containing the results or errors.

Signals and NgRx are not mutually exclusive. You can use Signals for local UI state and NgRx for shared application state. Angular also supports converting between Signals and Observables when needed.

My recommendation for your interview: Be ready to explain why you would choose a simple service or signal-based service first, and when a centralized NgRx Store becomes worthwhile.

9. Important NgRx interview questions and answers

                
Q1. What is the difference between an action and a reducer?
Answer: An action describes an event that occurred. A reducer defines how the current state changes in response to that action.

Q2. Why must reducers be pure functions?
Answer: Pure reducers produce predictable state updates, are straightforward to test, and avoid hidden side effects. They should not mutate existing state or perform HTTP requests.

Q3. What is the difference between a selector and an effect?
Answer: A selector reads or derives state. An Effect handles side effects such as API requests and can dispatch a resulting action.

Q4. Can we call an API inside a reducer?
Answer: No. Reducers must remain pure and synchronous. API requests belong in services, orchestrated by Effects when using NgRx.

Q5. What is the difference between createAction() and createReducer()?
Answer: createAction() defines an event, while createReducer() defines the state transitions associated with actions.

Q6. Why use props()?
Answer: props() defines the payload an action can carry, such as an employee ID, form data, or an API response.

Q7. What happens when an API request fails in an Effect?
Answer: The Effect should handle the error and emit a failure action. The reducer can then update the error and loading state. Handling the error inside the request's inner Observable also allows the outer Effect stream to continue listening for future actions.

Q8. What is memoization in NgRx selectors?
Answer: A memoized selector can reuse a previous derived result when its input values or references have not changed. This avoids unnecessary calculations.

Q9. What is the difference between switchMap() and exhaustMap() in an Effect?
Answer: switchMap() switches to the latest inner Observable and unsubscribes from the previous one. exhaustMap() ignores new source emissions while the current inner Observable is active.

Q10. Is NgRx required in every Angular project?
Answer: No. For simple applications, component state, services, or Signals may be sufficient. NgRx is useful when shared state, complex workflows, debugging, and predictable state transitions justify the additional structure.

Section 11 — Angular Performance Optimization

Performance optimization means improving how quickly an application starts, renders its content, responds to user actions, and processes data—without breaking functionality.

For interviews, remember these four areas:

  • Initial load: How quickly the application starts.
  • Rendering: How efficiently Angular updates the DOM.
  • Runtime: How smoothly the application responds to user interactions.
  • Network: How efficiently APIs, images, JavaScript and other resources are loaded.

11.1 Change detection optimization

Angular change detection determines when components need to be checked and their rendered views updated.

                    
Default          vs OnPush
Default strategy	OnPush strategy
Checks components according to the normal change-detection traversal and applicable triggers	Allows Angular to skip eligible component subtrees when they don't need checking
Convenient for simple applications	Useful for predictable, component-oriented rendering
Can perform unnecessary work if components are poorly structured	Works particularly well with immutable data and reactive state

11.2 Lazy loading vs eager loading

Eager loading loads feature code as part of the initial application loading path.

Lazy loading defers loading feature code until it is required, such as when a user navigates to a route.

11.3 Preloading strategies

Preloading fetches lazy-loaded route code in the background after the initial application load.

Angular supports strategies such as:

  • NoPreloading — do not automatically preload lazy routes.
  • PreloadAllModules — preload eligible lazy-loaded routes.
                    
                        import  provideRouter, withPreloading, PreloadAllModules  from '@angular/router';
                        providers: [
                        provideRouter(
                            routes,
                            withPreloading(PreloadAllModules)
                        )
                        ]

Important: This is not a guarantee that every resource in every route is loaded immediately. It applies to eligible lazy route configurations.

Interview question: If lazy loading reduces initial bundle size, why would you preload?

Because users may navigate to a feature shortly after the application starts. Preloading can reduce the wait when they navigate, at the cost of additional background network and processing work.

11.4 The @ defer block

@ defer allows Angular to defer eligible template dependencies until a trigger occurs.

For example, a dashboard may contain a large chart that users only see after scrolling.

A deferred block can improve perceived performance, but dependencies must be eligible for deferral. If the same dependency is used eagerly elsewhere, it may already be loaded.

11.7 Debouncing and throttling

These are JavaScript/RxJS techniques for reducing excessive work triggered by frequent events.

Debouncing: Waits until events stop arriving for a specified duration.

Throttling: Limits how often an operation is allowed to run over time.

Example: Search while typing.

Why use these operators together?

  • debounceTime(300) waits for a 300 ms pause.
  • distinctUntilChanged() skips consecutive duplicate values.
  • switchMap() switches to the newest request when a new search value arrives.

This is useful for autocomplete, filtering, and search forms.

11.8 Bundle size and tree shaking

Bundle size refers to the JavaScript, CSS and other resources required to run the application.

Tree shaking removes unused code when the build system can determine that it is safe to eliminate.

Other optimization techniques include:

  • Avoiding unnecessary large dependencies.
  • Importing only what the application needs.
  • Lazy-loading feature routes.
  • Using production builds.
  • Inspecting build output and bundle reports.
  • Compressing resources on the server where supported.

Useful commands:ng build, ng build --configuration production

The production build applies the configured production optimizations.

Interview question: What would you do if your Angular bundle is too large?

Answer: Inspect the bundle report, identify large dependencies, remove unused imports and libraries, lazy-load features, defer heavy components, and verify the effect by comparing production build output.

11.9 Memory leaks and subscriptions

A memory leak occurs when objects or subscriptions remain reachable longer than intended, retaining resources unnecessarily.

For Angular subscriptions, useful approaches include:

  • Using AsyncPipe in templates.
  • Using takeUntilDestroyed() for imperative subscriptions.
  • Explicitly unsubscribing from long-lived subscriptions when necessary.
  • Cleaning up event listeners and timers.
  • Avoiding accidental retention of large objects.

The example assumes EmployeeService.getUpdates() returns an Observable. The subscription is automatically cleaned up when this component is destroyed.

11.10 Performance profiling

Don't optimize based only on guesses. Measure first.

Useful tools:

  • Chrome DevTools Performance panel — identifies long tasks and expensive runtime operations.
  • Network panel — shows slow API requests, large resources, and repeated requests.
  • Angular DevTools — helps inspect the component tree and profile change detection.
  • Angular CLI build output — helps assess bundle size.

Real-world interview scenario

Question: A dashboard containing 20 charts and a table with 5,000 records is slow. How would you improve it?

                    
A strong answer:
1. Profile the application to identify whether the bottleneck is network, JavaScript, rendering, or change detection.
2. Defer below-the-fold charts using @ defer.
3. Use stable tracking for table rows and virtual scrolling if appropriate.
4. Reduce redundant API calls and introduce suitable caching where the data requirements allow it.
5. Use lazy-loaded routes and review large dependencies.
6. Apply OnPush or reactive state patterns where useful.
7. Measure again to confirm the improvements.

What is NgRx?

NgRx is a state management library for Angular applications based on the Redux pattern and powered by RxJS Observables.

Why Do We Need NgRx?

In small apps:

  • We use Input(), Output()
  • Services with BehaviorSubject
  • Direct data sharing

In large apps:

  • Multiple components need same data
  • Complex API flows
  • State must persist across routes
  • Debugging becomes hard

NgRx solves:

  • Centralized state
  • One-way data flow
  • Predictable state updates
  • Easy debugging with DevTools

Data Flow (One-Way)

  • Component dispatches Action
  • Action goes to Reducer
  • Reducer updates Store (state)
  • Component selects data from Store
  • If API needed → handled by Effects

Core Concepts of NgRx:

1. Store

  • Central state container
  • Immutable
  • Read-only (can only change via actions)

2. Actions

Actions describe what happened

3. Reducer

Reducer defines how state changes

4. Selectors

Used to read data from store

5. Effects (For API Calls)

Effects handle:

  • HTTP requests
  • Side effects
  • Async operations
